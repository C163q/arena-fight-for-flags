# 参赛题包的生成与维护

本说明供维护项目和制作题包的人阅读；不放入参赛压缩包。参赛者可以是人类程序员或 LLM，交付目标是独立实现符合 C ABI 的动态库。

## 一键生成

在仓库根目录运行：

```sh
python3 scripts/package_contest.py
# 或生成到新的目录
python3 scripts/package_contest.py --out dist/contest-kit-new
```

需要 Linux x86_64 GNU/glibc、Rust/Cargo 工具链和 GNU readelf。默认输出 `dist/contest-kit/`，目录已存在时拒绝覆盖。正常入口总是执行 `cargo build --locked --release`，选择裁判、worker、基准 AI、计时器这四个包，显式使用 GNU x86_64 目标、优化级别 3、关闭调试信息及 debug assertions、去除可移除符号。

编译设置使用受控的最高优先级 rustflags，覆盖外部目标平台参数；构建后检查实际 ELF 不含调试节/普通符号表，基准库保留四个 ABI 导出。

构建缓存独立位于 `target/contest-build/`，不从现有普通 `target/release/` 拿旧文件。打包失败只清理本次暂存文件，不删除既有输出。默认的 `dist/` 与构建缓存由 Git 忽略；自定义输出建议仍放在 `dist/` 下，或仓库外，避免误提交二进制。

```text
contest-kit/
  README.md             场外组织者说明，含题包与计时器哈希
  fff-timer             仅由场外人员手动操作
  participant.tar.gz    分发给参赛者的材料
```

只把 tarball 提供给参赛者，解压后在 `fff-contest/` 工作。外层计时器不进入 tarball；工作目录不能替代工具权限隔离，agent 若可读取外层目录仍能找到计时器。

## 旧题包归档

`dist/` 顶层只保留当前分发题包，旧版本移至 `dist/archive/<原目录名>/`，保留原始内容和权限。归档清单 `dist/archive/inventory.json` 记录构建信息、文件大小及 SHA-256；不提交题包或本地清单。历史报告中的旧 `dist/<题包名>/` 路径按此映射查找，不改写历史构建信息。

只移动完整分发题包；已被测评计划引用的解压工作区保留原位，以免破坏原计划的工具路径。具体归档批次和当前分发版本以本地归档清单为准。

## 固定文件范围

多 AI、多地图 league 编排器当前仅供场外人员使用，不加入参赛压缩包；参赛者使用小规模 selftest 和原固定名单自测器。打包白名单不随新增维护者脚本自动扩大。

压缩包包含 `bin/` 下的 runner、worker、timer-query；`lib/` 下的基准 AI；C 头文件、七张 RON 地图、专门的参赛 README/docs、测评脚本及其所需模块、示例配置、回放导出器和离线播放器资源。路径与具体文件白名单在 `scripts/package_contest.py` 中显式列出，不递归复制工具目录。

内层 `manifest.json` 记录格式/ABI 版本、源码提交与是否有工作区修改、工具链、平台、所需最低 glibc、文件 SHA-256 和权限。同样的文件与构建信息生成相同 tarball 字节；不保证不同工具链或环境下重编译产生相同 ELF。题包不捆绑 glibc/libgcc，需要在目标比赛环境验证兼容性。

不分发引擎、裁判、基准 AI、SDK 或接口库源码，不包含 `.rs`、`.rlib`、测试夹具、内部设计/审查/报告、历史对局或缓存。只提供 C 头文件和接口文档作为绑定依据。Python/JS 辅助工具是明确允许公开的内容。去除符号不等于二进制不可逆向。

## 专用文档与披露边界

模板在 `packaging/contest/organizer/` 和 `packaging/contest/participant/`。不要直接把项目 `docs/` 复制进题包。

后续修改以正式模板为准。需要保留原文对照时，可在独立目录中修改审阅副本，定稿后同步正式模板；副本不加入打包范围。审阅经过和验收结果放在 `docs/reviews/`、`docs/reports/`，本指南维护通用操作要求与编写规范。

- API 必须完整，包括所有字段、类型、顺序、数组长度、尺寸/对齐、哨兵值、坐标、生命周期、返回码、计算时间限制与内存限制。Rust 参赛者自行照头文件声明 `repr(C)` 类型和 C ABI 导出函数，无需与裁判使用相同版本的 Rust。
- 玩法说明覆盖基础行动、战斗、携旗、得分和基本冲突规则，旗点只概述为随机产旗。省略精确刷新生命周期、调度与失败重试、复杂移动依赖、随机算法和基准策略。
- ABI 已公开的运行参数仍如实说明，不删减头文件，不伪造数值。原始回放及辅助工具保持原样，参赛者可以通过实验推断题面未展开的规则。
- 自测说明必须说明测试规模（全人数 balanced 每块 198 场、五块 990 场），建议从两场 2p quick 起步；`run --jobs N` 默认 1，解释资源争抢/超时代价，明确正式评测固定 1。外层与内层 README 同步提醒，混合续跑保留并行自测标记。题包仅提供可执行的并发建议，不包含开发机硬件型号、探针方法或详细容量档位；这些测量细节保留在维护者实测报告。
- 不提供完整 AI 示例或策略 SDK，不把超过基准等同于最终胜出。参赛 README 明确要求持续测试与改进，提醒其他 LLM/程序员的 AI 可能显著强于基准。

当前题包的计算时间限制为比赛第 1 回合 250ms、其余 50ms，重启不改变这一规则；`CtfInit.decision_budget_us` 固定传入常规回合的 50000µs。默认地图 v3 最近取旗距离为 6–8 步，目标分为 20。已有题包不会自动更新，应生成新目录；已冻结的旧测评计划继续使用旧输入，新版本另建赛程，不能混合续跑。

自测报告采用千分制积分与区间，按未取整名次分排序；保留原始 0–1 统计字段以兼容既有分析。平均夺旗分不缩放。旧题包保留原版本，重新生成的新题包包含更新的报告工具和说明。

修改 ABI、地图、命令或播放器时，检查专用文档和白名单是否同步。精简文档应省略细节，不能编造不同规则。若未来需要连运行参数或回放数据也隐藏，须单独设计协议与记录变更。

## 参赛文档的组织与措辞

以下要求适用于 `packaging/contest/**/*.md`。面向掌握基础编程、但可能不熟悉动态库、C ABI、进程管理和测评工具的读者。文档应让他们能独立完成编译、接入、自测与提交；必要的解释可以展开，不要求读者先了解项目内部架构。

### 按任务组织内容

| 文档 | 应帮助读者完成的任务 |
| --- | --- |
| 参赛 README | 明白要实现和提交什么，找到阅读顺序，完成第一次检查和两场自测，了解时间要求 |
| 规则说明 | 理解行动、射击、携旗与得分，区分已说明的规则和需要实验探索的细节 |
| 接口说明 | 准确实现函数与数据结构，查到字段、内存使用、返回值和运行限制 |
| 自测说明 | 从小规模测试开始，选择地图与对手、比较版本、查看结果和继续未完成的测试 |
| 回放说明 | 找到单场记录，导出、打开播放器并定位具体回合的事件 |
| 场外 README | 准备运行环境与文件权限，控制计时，收取提交并安排正式评测 |

先写常见任务，较少使用的配置、统计和备份功能放在后面，供需要时查阅。一个章节集中回答同一类问题：例如积分章节解释计算与排序；某工具的报告怎样分组、文件保存在哪里，应放在该工具的使用说明中。

### 用具体行为解释术语

- 操作说明优先写“你的 AI”“正在测试的版本”“保存创建测试时的库和地图副本”，避免把“候选”“冻结”“快照”等内部简称直接作为读者必须掌握的概念。
- 必须出现的术语在首次使用时解释其含义及用途，例如动态库、C ABI、导出函数、随机种子和退出码。代码标识符、字段名和文件名保持准确，不能为了通俗而另造名称；报告中的 `candidate` 等名称，应与中文含义对应说明。
- 描述工具实际检查或执行什么，不加没有帮助的修饰。例如“两回合检查”应说明它会加载并调用 AI，能发现哪些问题，通过后又不能证明什么；不要用“私有”“真实 worker”等词代替这些说明。自动启动的辅助程序只需说明用途，无须让参赛者学习如何管理它。
- 用“计算时间限制”“内存限制”说明约束，不用“预算”“优惠”代指。写明限制作用于全队一次调用还是单个棋子，如何计时，以及故障后的处理。接口字段实际传入的数值与特殊回合的规则分别解释，避免让读者误以为字段会随回合改变。
- 句子写清对象与适用范围。例如写“旗帜未来的生成回合”，而非单独写“未来生成时间”；写明由哪个工具生成哪个报告，不把某工具的排名方式泛指为整个评测系统的行为。

### 给足操作信息，控制展开范围

命令示例应说明在哪个目录运行、需要先准备什么、预计执行多少场、结果写到哪里，以及接下来查看哪个文件。涉及继续执行时，写明它沿用哪个版本；修改代码后的新测试与旧记录续跑不能混为一谈。优先用两场自测等小规模示例，扩大测试前说明时间、空间和并行资源争抢的代价。

需要读者采取行动的失败情况，应给出下一步：例如库加载失败时核对接口，环境权限不足时把报告交给场外人员。系统隔离、计时器共享状态等配置放在场外说明中，参赛者只需知道如何查询和报告问题。

接口与运行限制必须足够完整；玩法和策略仍遵守上述披露边界。用简短例子解释距离、字段或命令的含义，不提供完整策略示例，也不把文档扩展成通用的操作系统或编程教材。完成记录、开发机测量和内部审查经过不放入参赛文档。

修改后按参赛者实际顺序通读：是否能知道下一步做什么，术语是否在使用前解释，是否有对象不明或范围过大的断言。然后核对当前实现、C 头文件、命令参数、文件路径与播放器界面。需要简化时减少非必要细节，不能删掉正确接入必需的约定。

## LLM 计时与场外操作

外层和内层 README 均须说明：LLM 的设计、编码、编译、自测时限为 **60 分钟**；**70 分钟**由场外人员强制终止会话并收取当时已有编译结果，无结果视作弃权，不等待补编译。LLM 必须时常执行 `bin/fff-timer-query`，只读查询总时间。人类程序员的时间安排另行约定。

场外人员启动与退出 `fff-timer`，维护计时与 agent 的文件权限，收取 `submission/libteam.so`、依赖说明和哈希，再安排正式名单、多次完整换位块对抗。计时器不自动结束会话，题包脚本也不控制 agent。共享 `/tmp` 的全局单例计时器要求有关场次依次计时。新查询器支持单独的 PID 命名空间，包括查询宿主旧版计时器；沙箱需共享同一状态 inode 与 `CLOCK_BOOTTIME` 时间基准，独立 `/tmp` 或时间偏移不在支持范围。升级只读查询器不要求重启计时器，已有题包需重新生成或由组织者分发已校验的新查询器，不能假定旧二进制自动修复。

收取多份提交后，可在场外使用 [league](league.md) 自动组合与补位。以规范入口 `submission/libteam.so` 为准；若目录中另有不同的“final”库，记录并确认实际收取哪份。冻结库与地图后统一使用同一裁判与时间限制比较，保留原题包版本；不能把旧版开发条件下的差异直接解释为模型能力差异。

## 维护参考

评估参赛流程和测试规模时，可参考 [参赛体验报告](../reports/contest-kit-selftrial-2026-10-16.md) 与 [三份提交统一评测](../reports/submissions-2026-10-16.md)。使用报告结论时注意其题包版本、样本和适用范围；开发者已有知识影响参赛体验，不能将其当作严格盲测。

已提供 [开发自测工具](selftest.md)：`check` 先诊断真实环境/ABI，`run` 默认两场，`compare` 分别对固定对手共享条件，`resume` 使用冻结输入，`summary` 分析公开事件并估算空间，`archive`/`restore` 验证完整记录的非破坏备份。`scripts/selftest.py` 与六个 `contest_lib` 模块均为显式白名单；不自动加入其他维护者模块。恢复仅离线备份，不迁移续跑。预检失败不改变正常比赛故障计分。

文档审阅方法与问题示例见 [审阅记录](../reviews/contest-documents-2026-10-17.md)；未完成的改进与后续工作见 [准备清单](../design/contest-kit-improvements.md)。

## 检查

```sh
python3 -m unittest discover -s tests -p 'test_*.py' -v
python3 -m unittest discover -s viewer -p 'test_*.py' -v
python3 scripts/generate_maps.py --check
python3 tests/contest_package_integration.py \
  --kit dist/contest-kit --out /tmp/fff-contest-check-new
```

独立验收输出目录必须是仓库外的全新目录；脚本保留解压题包、日志和真实对局。它先检查文件哈希、内部链接和禁止文件，再复制测试专用的 C/Rust 绑定（这些源码不在题包中），独立编译动态库，生成 2–8 人赛程，执行双人完整换位块并恢复/重建报告，执行 C/Rust 互战与八人对战，验证回放并导出 HTML/JSON；额外从解压包执行新工具预检、两场短自测、四场短版本对照与续跑、摘要、归档和恢复（合计12场真实比赛，其中8场仅两回合）。

验收只运行查询器，不启动、停止或接管计时器。真实对战需要 Unix socket 与子进程信号权限；普通 Python 单测使用真实组装逻辑与 ELF 文件，完整 ABI 行为由独立真实验收覆盖。
