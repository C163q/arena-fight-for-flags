# AI C ABI 草案

本文件定义候选接口契约，不是已发布的头文件。全图及所有棋子的坐标、血量、携旗状态已经确认；实现前还需确认 [D01 补充、D03、D04、D12](decisions.md)，再给出可编译的 Rust 定义与 C 头文件并做布局验证。

## 交付与调用方式

推荐 AI 是 Rust `cdylib`，首版产物为 Linux `.so`；其他语言将来可以提供相同导出符号。每队有一个独立 worker，只加载该队的库。三名棋子共同调用一次决策函数，不能分别获得三个 50ms 预算。

建议 ABI v1 导出以下符号，C 声明形状如下；其中 `CtfInit`、`CtfObservation`、`CtfTeamAction` 的最终布局由实现阶段头文件定义。

```c
uint32_t ctf_abi_version(void);
int32_t ctf_create(const CtfInit *init, void **context_out);
int32_t ctf_decide(void *context,
                   const CtfObservation *observation,
                   CtfTeamAction *output);
void ctf_destroy(void *context);
```

Rust 对应导出使用 `extern "C"`、无符号改名，以及 `#[repr(C)]` 数据结构。ABI 固定整数编码，不能跨边界传递 Rust 原生枚举；Rust 版本对应的导出属性语法在真正建立 workspace 时确定。

`ctf_abi_version` 返回 1。版本不支持、符号缺失、初始化失败视为加载故障，不尝试猜测布局。ABI 版本和 worker IPC 协议版本是不同版本域，分别校验。

## 生命周期与所有权

1. worker 加载库，调用版本查询，校验必需符号。
2. 调用 `ctf_create`，传入比赛配置、队伍 ID、独立 AI 种子和是否因故障重启等信息，获得库私有 context。无状态实现可合法返回空 context。
3. 每队每个回合调用一次 `ctf_decide`；不同队伍之间也串行调用，同一个 context 不会同时被两个线程调用。所有队伍接收同一个回合开始状态，各队调用之间不执行游戏动作。
4. 正常结束调用 `ctf_destroy` 并卸载库。进程被终止时不保证调用析构。

输入缓冲区由 worker 持有，只在当前调用期间有效。AI 可以复制内容进入自己的 context，但不得保留输入指针。输出缓冲区也由 worker 持有，AI 不负责释放；context 由 AI 创建并仅由其自身销毁，不跨 allocator 释放对象。

不得修改输入、保存输出指针到调用结束后、将后台任务延续到函数返回之后，或让 panic/异常 unwind 穿过 ABI。AI 可以在自己的边界内捕获失败并返回非零状态；进程 abort 或未捕获故障由裁判按 worker 失败处理。

## 数据布局原则

- 结构体使用 `#[repr(C)]`；标量使用 `uint8_t`、`uint32_t`、`int32_t`、`uint64_t` 等对应类型。
- 不使用 Rust `bool`、`usize`、引用、`Vec`、`String`、trait object，或依赖 Rust 枚举默认布局。
- 切片通过只读指针和明确的元素数量表示；数量为零时允许空指针，有元素时必须指向合法缓冲区。
- 顶层结构包含 `abi_version` 与 `struct_size`。v1 只接受 v1 明确规定的布局，不用长度字段假装自动兼容未来版本。
- 整数范围、数组长度、状态编码、无坐标时的表示、padding 与目标架构在头文件中明确；不把进程内 ABI 直接写入磁盘或 IPC。
- C 与 Rust 双方需要验证结构体尺寸、对齐及关键字段偏移，并通过一个实际动态库调用例子验证互操作。

## 初始化输入

`CtfInit` 建议包含：

| 信息 | 说明 |
| --- | --- |
| ABI 信息 | 版本与顶层结构大小 |
| 比赛与队伍 | 稳定比赛 ID、己方队伍 ID、2–8 队的队伍数量、每队三棋子的常量 |
| AI 种子 | 独立于引擎随机流的显式种子 |
| 生命周期信息 | 首次启动/重启标记、重启次数、即将服务的回合编号 |
| 比赛规则 | 地图宽高、最大血量 3、命中伤害 1、无自然回血、射程度量 Manhattan/距离 5、仅目标格受伤、友伤开启/自射禁止、死亡原格掉旗/携旗禁止移入地上旗格，以及回合/分数上限、复活缺席轮数、旗帜刷新区间 |
| 预算 | 决策时限 50000 微秒；实际由裁判强制执行 |

地图地形和出生区可以在每回合 observation 中引用完整只读视图，使重启不依赖此前调用。尺寸来自运行时加载的 RON；队伍列表最多 8 队，棋子列表为 `team_count*3`，最多 24 个。正式布局需规定最大地图尺寸并检查整数乘法溢出与缓冲区容量。

血量、伤害、射程等已确认常量通过接口报告，不能由参赛 AI 或比赛配置改写。射程字段应表达距离 5 与度量方式，不再使用“射程平方”字段；曼哈顿距离不改变弹道是一条直线的事实。

旗帜规则应报告为无自动过期、交回消失后才开始重刷；来源旗点 ID 不因拾取、携带或掉落改变。刷新范围通过初始化配置字段 `flag_respawn_min_turns`、`flag_respawn_max_turns` 报告，当前默认 5、15，均包含端点，默认分布为整数均匀随机；校验 `1<=min<=max`。这两个值可随后续平衡调整改变，不固化成 ABI 常量；AI 从本场配置读取，未来实际刷新时刻仍不放进观测。

初始化规则还报告开局立即生成数量公式 `max(1,(N+1)/3)`，使用整数除法，即约三分之一且至少一个；其余首次生成使用当前 5–15 回合延迟。选中旗点的结果体现在正常观测中的当前旗帜列表；未到期旗点的具体首次生成回合仍不传给 AI。选中数量由引擎按固定规则计算，不由 AI 决定。

正式回合的生成发生在所有棋子移动之后：未携旗者占据旗点则生成并立即携旗，已携旗者占据则失败、重新随机等待 5–15 回合。AI 读取的是本回合开始状态；本回合稍后生成的旗及即时携旗结果进入结束状态与下一回合观测，不能提前混入本回合输入。

## 观测输入（全图已确认，字段布局草案）

`CtfObservation` 建议提供：

| 信息 | 内容 |
| --- | --- |
| 回合信息 | 比赛 ID、当前回合、己方队伍 ID |
| 地图 | 宽高、按 `index=y*width+x` 排列的静态地形数组；旗点、出生区列表 |
| 队伍 | 稳定队伍 ID 与当前得分 |
| 所有棋子 | 队伍/棋子 ID、存活标记、坐标、当前血量、携旗 ID、复活计时/等待出生格状态 |
| 所有当前旗帜 | 旗 ID、来源旗点、地上坐标或携带者 ID |

死亡棋子用显式存活标记区分，坐标固定为 `(-1,-1)`，血量为 0。无携旗使用明确的标记字段，不能与合法 flag ID 冲突。列表按稳定 ID 排序。

AI 不看到其他队伍本回合提交、未来随机值、未来具体旗帜刷新时刻、引擎 RNG 状态或其他 AI 内存。完整回放内部状态与 AI observation 是不同类型，不能把前者原样传给 AI。

全图与所有棋子的坐标、血量和携旗状态是必须字段。复活信息建议提供 `respawn_at_turn` 及是否因出生区满员延迟；比分、当前旗帜列表等补充可见信息仍见 D01 补充，不将用户确认的核心信息重新标成待确认。

## 动作输出

`CtfTeamAction` 为带版本/结构大小的固定三槽位结果，按己方 `unit_id=0,1,2` 排列。每槽包含 unit ID、动作类型、方向、目标 x/y。未使用字段必须置零，死亡棋子填写等待。

| 字段编码 | 建议值 |
| --- | --- |
| 动作类型 | `0=Wait, 1=Move, 2=Shoot` |
| Move 方向 | `0=Up, 1=Down, 2=Left, 3=Right` |
| Shoot 坐标 | 有符号 32 位 x/y；越界按非法动作处理 |

射击提交仅指定一个目标格，不包含伤害、路径或命中对象。引擎检查目标范围与 `1<=abs(dx)+abs(dy)<=5`、射手存活/未携旗等条件；目标等于射手当前坐标时以 `self_target` 拒绝，非法动作不执行并规范化为等待。其他棋子占据目标格不构成非法条件，合法命中友军同样扣 1 血。合法射击的直线路径由引擎计算，只有指定格可能扣血，不能把途中棋子当作受伤目标或遮挡物；途中棋子不挡弹，障碍仍挡弹。

携旗者若提交移入有地上旗帜的格子，引擎在射击及死亡掉旗后以 `carrying_cannot_enter_flag` 拒绝该棋子移动、保持原位。校验基于移动阶段快照，不能只在收集动作时检查：本回合射击新产生的掉旗也可能使原先无旗的目标格变为非法。原始 Move 与最终采用的 Wait 都记入回放；该失败不使整队等待，也不允许 AI 重新提交动作。

worker 在调用前初始化结果缓冲区，并将槽位 ID 设为非法哨兵。AI 必须写出三个正确槽位并返回成功；不能靠初始化的等待值掩盖漏写结果。

API 返回码建议为 `0=成功, 1=输入不支持, 2=内部失败`，其他非零也按失败处理。非零时忽略整份输出。返回成功但外层版本、大小或槽位 ID 错误，同样整队等待；动作类型、方向或游戏坐标非法则只影响该棋子，具体游戏校验由引擎负责。

## 50ms 的含义

推荐 50ms 为每队每回合完整请求的墙钟预算，包含 IPC、AI 调用、返回及响应校验，不是每棋子 50ms，也不只计 CPU 时间。初始化另有限额，不能在初始化中预先获知或计算本轮动态局面。

各队串行调用已确认：计时在该队实际执行窗口开启时开始，等待前面队伍完成的时间不计入其预算。不得同时派发所有请求并从统一时刻计时，否则后调用的队伍会因排队被错误判超时。调用窗口外不得继续后台计算；runner 的暂停/恢复与进程清理由架构层实施。

输出必须完整返回才被采用，截止前写了一部分也不算成功。超时强制终止对应 worker，整队本回合等待；下一回合可以重启，但 context 丢失。AI 应留出序列化与调度余量，通常远早于 50ms 返回。

硬件和系统负载会影响墙钟结果。每场比赛记录机器、构建模式与计时政策；比赛策略输出的确定性与实际运行时是否超时应分开评估。
