# 参赛题包设计

状态：2026-10-15 用户已确认整体设计并要求开始实现。用户已要求一键生成题包，并确认接入材料仅提供 C 头文件和接口文档，不提供 Rust 源码绑定或预编译 Rust 接口库。

## 目标与交付边界

为场外组织者与参赛程序员/LLM 分别提供材料。参赛者可以是不借助 AI 的人类程序员。场外人员准备环境、分发题包、启动计时并收集最终 AI；参赛者独立实现 C ABI 动态库，使用题包自测与查看回放。

参赛 README 应明确提示：提交的夺旗 AI 将与其他 LLM 或程序员编写的 AI 比拼，对手可能显著强于基准 AI。超过基准只是自测参考，参赛者应充分利用可用时间，持续测试、分析与改进，争取提交自己的最佳实现。

题包不改变现有引擎、ABI、计时器或测评行为。系统仍为 Linux 64 位；首版打包针对构建主机的 Linux x86_64 GNU 环境，记录工具链与系统依赖，不声称跨系统通用。参赛 AI 无需使用构建裁判时相同的 Rust 编译器，只需满足目标平台的 C ABI 和动态加载要求。

## 方案选择

采用独立参赛文档模板、显式文件白名单和预构建运行工具。相比从仓库文档自动删减，此方案容易检查披露边界；相比容器镜像，更接近用户指定的文件夹与 tarball，且无需引入容器操作步骤。

## 生成文件夹

默认输出到 `dist/contest-kit/`，整个 `dist/` 由 Git 忽略：

```text
contest-kit/
  README.md                 # 场外人员操作说明
  fff-timer                 # 人工启动的 release 计时器
  participant.tar.gz        # 只将这个文件提供给参赛者
```

外层 README 说明依赖检查、解压与工作目录、人工启动与退出计时器、为 LLM 限定文件访问范围、执行下述开发时限、收集最终动态库、校验题包及组织正式评测的步骤。agent 选择和正式参赛名单由组织者决定；本任务不增加自动启动计时器或终止 agent 会话的程序。

将计时器放在压缩包外是分发边界。若 agent 能访问外层目录，单靠文件布局不能阻止其操作计时器；组织者应只暴露解压后的目录或使用相应工具权限。打包器及普通验收不启动、停止或接管既有人工计时器。

压缩包固定包含一个顶层目录 `fff-contest/`：

```text
fff-contest/
  README.md
  bin/fff-runner
  bin/fff-ai-worker
  bin/fff-timer-query
  lib/libfff_bot_baseline.so
  include/ctf_ai.h
  maps/arena_2p.ron ... arena_8p.ron
  docs/rules.md
  docs/api.md
  docs/testing.md
  docs/replay.md
  scripts/tournament.py
  scripts/tournament_lib/   # 运行测评所需模块
  config/tournament.example.json
  viewer/                  # 导出器、结构校验及离线 HTML/CSS/JS 资源
  manifest.json            # 版本、平台、构建信息及文件 SHA-256
```

不包含 `fff-timer`、Rust 源文件、`.rlib`、策略 SDK、AI 实现、测试夹具、仓库 `.git`、内部文档、历史比赛、缓存和调试构建。C 头文件是声明材料，Python/JS 是自测与回放工具，属于允许公开的辅助内容。只交付基准 AI 二进制，不附策略示例或等待 AI 源码。

## LLM 开发时限

以下要求同时写入外层场外人员 README 与内层参赛 README，专门适用于 LLM；人类程序员的时间安排由组织者另行约定。

- 场外人员在 LLM 开始参赛任务时手动启动 `fff-timer`。LLM 的设计、编码、编译和自测均计入总用时。
- LLM 的任务时限为 **60 分钟**，应在此时间内完成实现并准备好可提交的编译结果。
- 在总用时达到 **70 分钟**时，场外人员必须强制终止 LLM 会话，按截止时已经产生的编译结果收取，不等待继续生成或补编译。若没有编译结果，视为弃权；已有结果按正常接口与运行要求验收。
- LLM 必须时常运行 `bin/fff-timer-query` 查看经过时间，合理安排编译、自测与提交，并保留已完成编译的可提交产物。查询器只读，不能启动、停止或重置计时器；若查询失败，应报告场外人员处理。
- 总开发时限与对战中每队每回合的 **50ms** 预算是两种独立限制。`fff-timer` 不负责自动终止会话，70 分钟的强制终止和产物收取由场外人员执行。

## 参赛文档的披露规则

参赛材料独立维护，不复制项目内部规则、设计决策或审查报告。精简不等于描述错误规则，省略的机制可通过正式程序实验观察。

| 主题 | 公开程度 |
| --- | --- |
| 接入协议 | 完整说明四个导出函数、返回码、所有结构体字段/类型/顺序、指针数组长度、坐标、枚举编码、哨兵值、结构大小、所有权与有效期 |
| Rust 接入 | 说明自行按头文件声明 `repr(C)` 类型、使用 `extern "C"` 和正确符号导出，编译为 cdylib；不提供 `.rs`、项目策略实现或完整 AI 示例 |
| 运行约束 | 明示每队三个棋子、50ms 整队预算、串行同快照、初始化和内存限制、故障等待及重启后记忆丢失 |
| LLM 开发要求 | 明示 60 分钟任务时限、70 分钟由场外人员强制终止并收取已有编译结果、无结果弃权，以及时常只读查询总用时；不将这些额外要求施加给未使用 LLM 的人类程序员 |
| 竞争目标 | 明示将与其他 LLM/程序员的 AI 比拼、对手可能显著强于基准，要求参赛者持续测试与改进，发挥最佳水平 |
| 基本玩法 | 明示移动/射击/等待、HP/射程/友伤/墙体遮挡、携旗限制、回出生区得分、死亡掉旗与随后复活、先射击后移动、争格和友军/敌军交换的基本行为 |
| 旗帜生成 | 玩法文档仅说明旗点随机生成；不展开开局取整、独立旗源生命周期、交旗后的计时、失败重试、生成阶段和随机算法 |
| 其他边界 | 不讲解完整移动依赖图、闭环判定算法、多旗优先级、复活抽样顺序或引擎实现 |
| 接口内规则参数 | 仍如实解释 `flag_respawn_min_turns/max_turns`、`initial_flag_count`、`respawn_absent_turns` 等字段的含义；不隐去或伪造 ABI 已公开的信息，不在说明中给推导公式 |
| 回放 | 提供验证、导出、播放和 ASCII 阅读入口；保留原始记录与播放器功能，不删改可观察事件或私有调度数据 |
| 评测 | 提供配置路径、名单、轮换、种子、续跑与结果解读的必要操作；不附基准策略分析、调参结论或历史强度报告 |

“隐藏机制”指不在题面讲解，不承诺无法从二进制、接口参数、自测脚本或原始回放推断。若未来要求这些信息也不可观察，需要另外修改协议与记录，不属于本次题包工作。

## 自测与交付

参赛 README 先引导阅读接口、实现和 release 编译，再说明将最终库放到 `submission/libteam.so`。这个目录及库由参赛者创建，题包不预置实现。

单局示例使用 `bin/fff-runner`、一份候选库与基准库；人数必须与地图一致。测评示例为每种人数配置一名候选与 N−1 个独立 ID 的基准副本，可通过 `--only 2p --mode quick --repeats 1` 快速检查，通过完整均衡换位块评估结果。测评器和回放工具在解压目录中独立运行，不引用仓库或 `target/release/`。

候选变更后需创建新评测计划，以免误用已冻结旧库。组织者正式比赛使用自己的名单和多个完整均衡块，收集动态库、依赖说明及哈希；参赛者只能查询总用时，无计时控制入口。

## 打包与维护

新增 `scripts/package_contest.py`，默认执行锁定依赖的 release 构建，再按白名单复制所需 ELF、头文件、七图、辅助工具、专用模板并生成清单和 tar.gz。不提供“直接复制任意旧 target 文件”的正常交付路径。输出已存在时拒绝覆盖，先在临时目录组装并校验后发布；失败仅清理本次临时文件。

专用模板保存在 `packaging/contest/`，参与版本控制；实际题包和构建缓存不进入 Git。二进制使用 release、关闭调试信息并去除可移除的符号信息；保留动态加载所需的 ABI 导出，不声称二进制不可逆向。

新增仓库维护说明 `docs/guides/contest-kit.md`，明确生成命令、文件白名单、允许公开/省略的内容、模板同步责任、工具依赖和验收步骤；同步文档导航、README 和 AGENTS。

## 验收

1. 单测检查文件白名单、压缩包顶层、路径安全、执行权限、文件哈希、拒绝覆盖与失败清理，以及禁止项未进入题包。
2. 检查参赛文档字段覆盖、内部链接有效，且没有指向仓库源码/内部文档的链接；核对精简题面与现有行为没有冲突。外层与内层 README 均需包含 LLM 的 60/70 分钟要求、无编译结果弃权和查询器用法；内层 README 需包含面向所有参赛者的竞争与改进要求。
3. 从生成的压缩包解压到仓库外的新目录，只用题包头文件构建测试用 C ABI 动态库，运行真实对战与 `verify`，确认不依赖仓库路径。
4. 在该目录验证测评计划/真实执行/报告与回放 HTML/JSON 导出；确认 2–8 人配置都能生成正确赛程。实际对局优先小规模，不为打包功能重跑完整 990 场。
5. 查询器可在有/无既有计时器时只读执行；验收不干预计时器。人工显示及计时生命周期仍使用既有计时器验收规则。
6. 执行相关 Python 单测、地图生成一致性、链接/差异检查。若改动 Rust 代码或计时器行为，执行对应 Rust 与真实进程测试；目前设计无需改变它们。

实现完成后生成一个可使用的实际题包并记录验收结果，按协作约定自行提交代码、模板与文档，生成产物保持忽略。
