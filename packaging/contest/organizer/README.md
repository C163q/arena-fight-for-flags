# Fight for Flags：场外人员操作说明

本页供组织比赛、运行 LLM 编程会话或收取提交的人阅读。你负责准备环境、向参赛者提供材料、为 LLM 开始计时、按时结束会话，以及收取和评测编译结果。

参赛者只需要收到 `participant.tar.gz`。它包含参赛说明、接口、地图、基准 AI、比赛和自测工具。外层的 `fff-timer` 是你操作的计时器，不交给 LLM 使用；压缩包内的 `fff-timer-query` 只能查询时间，不能控制计时。

## 1. 校验和解压材料

在本说明所在目录执行以下命令，核对文件是否与这次分发的版本一致：

```sh
printf '%s  %s\n' '@ARCHIVE_SHA256@' participant.tar.gz | sha256sum -c -
printf '%s  %s\n' '@TIMER_SHA256@' fff-timer | sha256sum -c -
```

每次参赛都使用全新的工作目录。例如：

```sh
mkdir participant-work
tar -xzf participant.tar.gz -C participant-work
```

解压后得到 `participant-work/fff-contest/`。把它设为参赛者或编程 agent 的工作目录；不要向 agent 开放外层计时器、项目源码或其他参赛者的文件。仅仅更改工作目录不能限制文件访问范围，还需要通过运行平台配置权限。

## 2. 开始计时前检查环境

比赛程序需要 **Linux x86_64 GNU/glibc** 和 `libgcc_s`，辅助脚本需要 **Python 3.10 或更新版本**。参赛者自行准备 Rust、C/C++ 等编译器。解压目录的 `manifest.json` 记录本题包要求的最低 glibc 版本。

进入解压目录，用题包自带的基准 AI 检查环境：

```sh
cd participant-work/fff-contest
python3 scripts/selftest.py check --ai lib/libfff_bot_baseline.so --out runs/environment
```

检查会先尝试运行基准 AI，再检查指定的库；这里指定的也仍是基准 AI，因此不会运行参赛者的实现。先读 `runs/environment/report.md`。权限不足或程序不能启动时，由场外人员处理后重新检查，使用新的输出目录。

环境准备可以在计时前完成。**LLM 一旦开始设计、编写代码或测试自己的 AI，就必须计入开发时间。** 计时后，参赛者自己的接入检查和自测也都占用时限。

将参赛 README 与任务要求一起交给参赛者，并明确：最终对手是其他 LLM 或程序员编写的 AI，他们可能明显强于基准，不能把战胜基准当作开发完成。

## 3. 为 LLM 开始计时

在 LLM 开始任务时，由人类在单独终端中进入本说明所在的外层目录，运行：

```sh
./fff-timer
```

保持这个程序运行。它从零开始计时，退出后重新运行会归零，没有暂停或继续功能。同一套共享计时环境只能运行一个实例，因此使用它的 LLM 场次要依次计时。

LLM 的设计、编码、编译、自测时限为 **60 分钟**。要求它时常在工作目录执行 `bin/fff-timer-query` 查看总用时，并在 60 分钟内准备好 `submission/libteam.so`。LLM 不能启动、停止、暂停、重置计时器或修改计时状态。

**到 70 分钟，场外人员必须强制终止 LLM 会话及仍在执行的编程任务，立即收取当时已经编译完成的结果，不等待补编译；没有编译结果则视作弃权。** 已有结果仍按正常接口和运行要求验收。建议参赛者在修改时保留一份已经编译、可提交的库。

计时器不会自动结束会话，需要你使用 agent 平台的控制功能执行截止。任务结束并收取结果后，再由人类退出计时器。查询失败或计时器意外退出时，由场外人员处理，不让 LLM 自行重启或重置。纯人类程序员的时间安排另行约定，不适用这项 LLM 专用时限。

### 如果 agent 在隔离环境中运行

请在正式开始前确认：agent 内运行 `bin/fff-timer-query` 能读到外层计时器的时间。计时器和查询器需要看到同一个 `/tmp` 状态文件，并使用相同的系统时间基准 `CLOCK_BOOTTIME`。仅隔离进程编号（PID）可以正常查询；独立的 `/tmp` 或带时间偏移的环境不能直接查询外层实例。不要为解决查询失败而让 LLM 接管计时器，应由负责环境配置的人处理。

## 4. 收取提交

收取约定位置的 `submission/libteam.so`，以及额外动态库依赖的说明。将文件复制到场外的评测目录，记录 SHA-256，例如：

```sh
sha256sum submission/libteam.so
```

如果参赛目录里有多个库，以 `submission/libteam.so` 为规定的提交入口；不要自行挑选名称带 `final` 的其他文件。检查收取的库能否加载，并验证实际比赛记录。缺少编译结果、接口不兼容和比赛中出现超时或崩溃是不同问题，应分别记录。

## 5. 安排正式比赛

正式评测使用本项目仓库中的 **`scripts/league.py`**，把收取的 AI 放在同一份参赛名单中，选择若干地图进行比较。它会根据地图人数安排组合和出生位置轮换，输出各地图排名与跨地图总榜。

**参赛压缩包不包含 `league.py`。** 场外人员需要另行准备本项目仓库；如果只拿到题包，请联系维护者准备正式评测环境。仓库和其他参赛者的文件不要向编程 agent 开放。下面的命令在项目仓库根目录执行，而非参赛者解压的 `fff-contest/` 中。

### 配置参赛者、地图和填充对手

将仓库中的 `config/league.example.json` 复制为 `config/league.formal.json`，替换示例内容：

- `participants`：本次收取的全部参赛 AI。每个 AI 使用唯一的 `id`，`library` 指向收取的动态库文件；不要保留未参赛的示例条目。
- `maps`：本次要评测的地图，每项填写唯一的 `id` 和地图文件路径 `map`。人数从地图读取，不需要为每张图另填参赛名单。
- `filler`：当参赛者少于地图人数时，用哪个 AI 填满剩余队伍。通常使用题包的基准库；各填充队独立运行，参与比赛但不进入排行榜。参赛者多于地图人数时，工具会安排多场组合，使各参赛者及任意两位参赛者的出场得到均衡安排。
- `runner`：本次统一使用的比赛程序路径。建议指向本次题包解压后的 `bin/fff-runner`，同目录保留配套的 `fff-ai-worker`；地图和填充基准也使用同一题包中的文件。

配置版本使用 `version: 2`。文件路径相对于配置文件所在目录，也可以使用绝对路径。所有提交使用同一份未修改的比赛程序、地图和评测规则，不能把不同题包下各自对基准的成绩拼成总榜。

### 先检查场数，再运行

例如，下面生成五次完整重复的正式赛程：

```sh
python3 scripts/league.py plan --config config/league.formal.json \
  --out runs/league-formal --repeats 5
```

`plan` 保存当时的 AI 与地图副本，显示计划场数，但不运行 AI。输出目录必须尚不存在。参赛者数量、地图和重复次数都会影响总场数，先检查规模并预留时间、磁盘，再开始：

```sh
python3 scripts/league.py run runs/league-formal --jobs 1
```

**正式评测固定 `--jobs 1`**，即一次只运行一场比赛。各地图的排名只使用完成且记录校验通过的整组比赛；总榜还要求同一重复序号下的所有指定地图都完成。总榜对各地图的积分取等权平均，不因某张地图场数更多而提高它的权重。

结果保存在 `runs/league-formal/report.md`、`standings.csv` 和 `results.json`，包括总榜、单图榜、得分、超时和故障等信息。按 Ctrl+C 可以中断，之后重新执行同一条 `run` 命令继续。续跑使用原计划保存的 AI 与地图；换库或换地图时新建计划，运行期间不要移动计划目录或替换比赛程序。

## 6. 提醒参赛者控制自测规模

参赛者可用 `--jobs N` 同时运行多场自测，但这会争用计算和磁盘资源，可能增加超时、改变成绩。正式测试应另建计划，不能把并行自测作为串行正式成绩。`tournament.py` 的完整 2–8 人 `balanced` 测试重复一次为 198 场，默认五次为 990 场，可能需要数小时；提醒 LLM 从 `selftest.py run` 默认的两场自测开始，按实际耗时扩大规模。

题包内的 `selftest.py`、`tournament.py` 供参赛者开发自测，操作见压缩包内的 `docs/testing.md`。正式比较使用上述场外 `league.py` 流程。

比赛程序会单独启动进程来运行 AI，以处理通常的超时或崩溃；这不等于已经能够安全执行恶意代码。运行外部提交时，场外人员仍需准备合适的系统隔离环境。
